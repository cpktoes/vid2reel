# Vid2Reel

A personal tool (package `v2r`) that turns iPhone clips into finished videos in two first-class shapes: **tall** 9:16 (1080×1920) for short-form reels, and **wide** 16:9 (1920×1080) for longer-form YouTube, often talking-head footage that stays landscape. No command, default or test may assume tall. It is not a website. It runs in the code sandbox of a Claude chat on a phone: a small skill in the user's Claude account clones this public repo, reads EDITOR.md and follows it. The user is my wife, a content creator working only from her iPhone. I am not a programmer: explain every change in plain English.

**Stack, on this Mac.** Python 3.13 via uv, FFmpeg, pytest: `uv sync`, `uv run pytest`, `uv run python -m v2r doctor | join --shape tall|wide FILES | build-skill`. The sandbox has no uv and installs `requirements.txt` with pip; regenerate it after any `uv add` (command in README.md).

**Three jobs that never mix.** `v2r/look/` only measures clips and makes sheets of stills; it decides nothing. The cut list (JSON, checked against `schema/cutlist.schema.json`) is the only place edit decisions live; at runtime the chat's Claude writes it, never code in this repo. `v2r/render/` builds exactly what a cut list says and makes no choices of its own. `v2r/normalize` converts every clip to one working format before anything else touches it. Originals are never modified; every output is a new file. Every number that controls behaviour (sizes, limits, how often to sample a still) lives in `v2r/settings.py`.

**EDITOR.md and taste.** EDITOR.md is the plain-English handbook the chat's Claude follows. I edit it myself: keep it short and plain, and never move its content into code or into the skill. It holds craft and house rules only. Taste never goes into EDITOR.md or anywhere in the repo: each social account has a "Reel style" section in its Claude Project's instructions, which outranks the handbook's defaults and is outranked by what the user types in the chat. The skill is account-wide and works in any chat.

**House rules.** No filters or colour looks unless the user's message asks; by default only a mild touch-up so the clips look like one shoot. In a tall reel every shot fills the frame: horizontal video is cropped to vertical, widescreen is never mixed in, no bars, no blurred backgrounds. Gentle movement (a slow push-in or pan) is welcome, especially on photos, and used sparingly. settings.py caps how much touch-up and movement is allowed; when to use them is the handbook's business. A good result outranks a short conversation: the chat's Claude asks a brief of three to five quick questions before editing, and everything must still be doable from a phone alone.

**The sandbox is the truth.** Python and FFmpeg only, packages from pip, files from github.com, no other network, no GPU, no paid services, no API keys. Its measured limits are in docs/phone-limits.md (30 MiB back at most; any command stopped after 2 minutes; FFmpeg 6.1). After any change to how video is processed, tell me to test from a phone before merging. You cannot watch video or hear audio: when a change affects how a reel looks or sounds, say exactly what I should look or listen for, and at what time in the video.

**Public repo.** Never commit video, photos or audio from fixtures/ or work/, anyone's name or account, or any secret. The reel log, the taste notes and the taste-profile drafts stay in fixtures/. No Co-Authored-By or other attribution lines in commits. Only public-domain (CC0) music goes in music/, each track with its licence and source in music/library.json. Before writing something from scratch, check whether a well-maintained open-source library already does it, tell me its licence, and list it in docs/licenses.md.

**The guide, decisions and workflow.** docs/field-guide.html is my plan, written for me: read only the stage I name; its Decide boxes are options until I say which; never act on it unprompted; never edit it: it is a snapshot of a guide I maintain elsewhere and replace when revised. The plan will change as we build. When I settle a Decide box, change my mind, or we build something differently from the guide, write the decision into this file and add a dated line to docs/decisions.md giving the stage, what was decided and how it differs from the guide; that file never names a person or an account. Where this file or docs/decisions.md disagrees with the guide, they win, because they are newer; tell me about the difference so I can have the guide revised. Settled so far: a public repo and a fetching skill (Stage 10); a wide clip in a tall reel is cropped to fill, centred on the subject (Stage 16); a brief of three to five questions (Stage 19); long videos are edited on a Mac throughout (Stage 23). GSD phases and git branches are named by guide stage ("Stage 14 – Normalize", branch `stage-14-normalize`), one phase per stage, never merged, split or reordered; the next stage starts only when the current one is merged. main is what her phone runs, so nothing merges into main until I have made a reel from a phone on the stage's branch.
